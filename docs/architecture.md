# 아키텍처와 역할

**한국어** | [English](architecture.en.md) · [문서 목차](README.md)

선택한 구조는 **독립 공통 엔진 + 라이브러리·CLI·LSP 어댑터**입니다.
Python으로 PoC를 만들고 검증한 뒤, 인터페이스와 관찰 가능한 동작을 유지하며 Rust로 점진 전환합니다.
아래 그림은 목표 구조이며 모든 연결이 현재 배포되었다는 뜻은 아닙니다.

![목표 구조: csql-future는 라이브러리, 편집기는 LSP, AI·CI는 CLI를 통해 공통 엔진을 호출합니다. 검증기는 별도 네이티브 CUBRID 파서 워커를 사용합니다.](../assets/readme/architecture.svg)

## 이 저장소가 소유하는 부분

| 구성 요소 | 책임 |
| --- | --- |
| 완성 코어 | 미완성 SQL·CSQL 명령의 문맥, 후보 순서, 식별자 인용, 별칭과 대체 범위 |
| 문법 검증기 | 프로파일 선택, 지원 범위 판정, 워커 수명, 문법 진단과 실패 분류 |
| 공통 값·계약 | 원문 범위, 스키마 스냅샷, 진단 코드·심각도, 버전 식별값 |
| CLI 어댑터 | 파일·표준 입력을 검사하고 사람용·JSON 결과와 종료 상태 제공 |
| LSP 어댑터 | 편집기 문서 버전·취소·위치 변환과 완성·진단의 프로토콜 전송 |
| 네이티브 파서 워커 | 고정 CUBRID 빌드의 파싱·오류 수집을 별도 프로세스에서 수행 |

언어 지식은 코어·검증기에 두고 어댑터에 SQL 엔진을 다시 만들지 않습니다.
Python PoC의 import 패키지는 `cubrid_language`입니다.
코어·CLI는 Python 3.10 이상과 필수 Python 런타임 의존성 0개를 목표로 합니다.
LSP는 선택적 의존성을 사용합니다. 엄격한 파싱에는 별도 검증된 네이티브 런타임이 필요합니다.

## 별도 제품이 소유하는 부분

- **csql-future:** 터미널 편집기, Ctrl+R 히스토리, 키 입력, 완성 메뉴, 접속·카탈로그 조회.
- **VS Code 확장:** 언어 ID, 파일 연결, 서버 시작 설정, 구문 강조, 들여쓰기와 편집기 명령.
- **Neovim 플러그인:** filetype, 내장 LSP 설정, 구문 강조·들여쓰기와 사용자 명령.
- **AI·CI 도구:** 린트 호출, 결과 처리와 각 작업의 정책.

각 제품은 별도로 패키징·배포합니다.
`csql-future`의 현재 자체 완성은 전환 전까지 유지합니다.
히스토리는 터미널 제품의 기능이며 공통 언어 코어의 기능으로 옮기지 않습니다.

## 실제 호출 경로

| 소비자 | 호출 경로 |
| --- | --- |
| Python 터미널 | 라이브러리 직접 호출 → 완성 코어 |
| VS Code·Neovim | 편집기가 소유한 LSP 자식 프로세스 → 코어·검증기 |
| AI·CI·셸 | 린트 CLI 프로세스 → 검증기 |
| 문법 검증기 | 소유한 네이티브 워커와 pipe의 UTF-8 JSON lines로 통신 |

LSP는 표준 입력·출력(stdio)을 사용합니다.
공유 daemon·localhost socket·TCP 수신 포트·호스팅 서버는 이 구조에 필요하지 않습니다.
“공통”은 유지보수할 구현과 계약이 하나라는 의미입니다.
완성 코어는 I/O 없이 본문·커서·프로파일·선택적 스키마를 받아 후보를 계산합니다.

## 완성과 문법 검사를 분리하는 이유

사용자가 작성 중인 `SELECT e.`는 파서가 거부하더라도 완성할 수 있어야 합니다.
따라서 완성은 엄격한 파싱 성공을 기다리지 않습니다.
DB 없이 검사하는 파서가 테이블·컬럼의 실제 존재까지 보장하는 것도 아닙니다.
문법 성공, 미지원 구문, 파서·도구 실패를 다른 결과로 유지합니다.

소스 범위는 원문의 Unicode 코드 포인트 기준 반열린 범위입니다.
LSP 어댑터는 이를 UTF-16 위치로 변환합니다.
Rust로 옮길 때도 바이트 인덱스를 그대로 편집기 문자 위치로 사용하지 않습니다.
한글·이모지·CRLF 코퍼스로 같은 대체·진단 위치를 확인합니다.

## CUBRID 네이티브 파서의 경계

초기 목표 프로파일은 `cubrid-11.5.0.2704-cc94778`입니다.
소스 `cc947788d3b7dc402f46192d0f3299ddcc8563ba`와 일치하는 라이브러리·헤더·런타임·설정을 검증합니다.
첫 제한 범위는 리터럴 SELECT와 CREATE SERIAL입니다. 후속 계열도 각각 검토·검증합니다.

입력 SQL을 실행하거나 DB에 접속하는 경로로 문법 검사를 대체하지 않습니다.
알 수 없는 빌드·미검증 구문·워커 부재는 성공 결과가 아닙니다.
네이티브 파서 재사용을 Rust 문법 재구현으로 바꾸는 것은 이번 언어 전환 계획에 포함되지 않습니다.

## Python PoC에서 Rust로

처음에는 Python으로 사용 흐름과 계약을 빠르게 확인합니다.
그다음 경계가 정해진 모듈을 하나씩 Rust로 바꾸고 같은 코퍼스로 결과를 비교합니다.
완성 후보·순서·대체 범위, 진단 코드·위치·상태, CLI 종료 코드·JSON, LSP 동작을 비교 기준으로 삼습니다.

LSP·CLI 프로토콜은 구현 언어와 독립적이므로 소비자와 내부 교체를 분리할 수 있습니다.
직접 Python import를 사용하는 제품에는 해당 단계에서 바인딩 또는 호환 계층을 정해야 합니다.
구체적인 FFI·바인딩 기술은 아직 선택하지 않았습니다.
검증 전에는 Rust 구현이 Python과 동등하거나 더 빠르다고 주장하지 않습니다.

단계와 배포 경계는 [개발·제품 로드맵](product-roadmap.md)에 있습니다.
